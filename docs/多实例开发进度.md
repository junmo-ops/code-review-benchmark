# 多实例开发与部署

## 已接通的链路

页面提交 → MySQL 登记批次 → Worker 创建不可变批次快照 → 案例任务分发给多个 Worker → COS 保存每次尝试 → MySQL 发布有效结果 → 唯一汇总任务评分、生成报告与归档 → 页面读取共享状态、日志和下载结果。

默认仍为单实例。启用 mysql 模式后支持 **N 个 Web + N 个 Worker**，没有共享目录或会话粘滞要求。上传会话、导入进度、资源清单版本和页面会话令牌由 MySQL 共享；文件保存在 COS，本地目录仅作缓存。模型配置使用独立私有 COS 前缀。

集群支持单轮 LCR、服务端 Agent、DSH，每 Worker 内部最多 5 个执行槽；资源任务与测评任务共用执行槽，对用户只暴露一个全局并发上限，新环境默认 5，不随实例数自动放大。多轮 MCR、c-CRAB、Cline、Skill 对照实验仍使用单实例部署。集群暂不支持原批次单例重跑和资源删除，界面/API 会提示；需要补跑可用所选案例新建批次。

## 执行与数据规则

- 新批次冻结模型配置到私有 COS 模型前缀；任务输入只保存配置文件标识，不在 SQL payload 或普通证据中保存凭据。Skill 内容随输入快照传递，批次继续校验冻结身份。
- 每个案例尝试在独立子进程、独立临时数据目录运行。Git/COS 仓库按当前案例准备，不为整批预建工作区。冻结提交和工具身份不改写。
- 调度任务包含工具身份摘要。Worker 只领取兼容版本任务；升级后要保留旧版本 Worker 直到其批次结束。没有兼容 Worker 时任务等待，不悄悄换版本。
- COS 使用带环境前缀的内容寻址对象；数据库中的结果指针是发布入口。旧实例即使还上传了对象，过期租约也不能发布或覆盖已生效结果。旧的整批 COS 定时同步在集群模式关闭。
- 运行中约每 30 秒上传检查点和脱敏日志尾部；检视完成后先上传证据，再提交 MySQL。日志页展示的是已持久化片段，可能有同步延迟；不是完整原始控制台日志流。
- 服务端 Agent 在创建请求前、拿到任务 ID 后等待持久化确认。接手有 ID 的任务继续查询；提交已发出但 ID 丢失时明确失败，不盲目重复提交。
- 质量模式每个案例最多领取 3 次；稳定性模式只领取 1 次，实例中断也保留为失败事实。正常执行失败不会自动创建另一条案例任务，LCR 原有冻结重试策略仍由适配器执行。
- 租约保证有效发布者唯一，不保证远端模型调用恰好一次。旧实例失联时远端请求可能仍在进行；接手不能伪装成首次成功。
- 所有案例达到终态才创建一个汇总任务；不同 Worker 的完整答卷汇入同一批次，沿用原评分口径。汇总任务中断后使用已上传的评分缓存继续；未上传的缓存仍可能产生重复评分请求。
- 报告附带 `cluster-execution.md`，原始证据附带 `cluster-attempts.json`，记录尝试次数和证据指针。丢失期间没有记录的 Token 与时间不按零估算。
- 暂停/取消立即禁止当前租约续期与发布；执行槽在租约结束后释放。Worker 退出会停止子进程，未发布任务按租约与次数上限处理。

## 部署配置

### 1. 数据库

部署依赖新增 PyMySQL（含 RSA 认证支持）。开发环境重新执行 setup 或安装 backend requirements；镜像依原有 Dockerfile 安装，无新增发布阶段测试。

数据库地址、端口和库名统一放在仓库的 `deployment/database.json`，随镜像发布：

```json
{
  "host": "codereviewst.tdsql.dbdns.cmbchina.cn",
  "port": 6666,
  "database": "codebench"
}
```

在部署平台为 Web 和 Worker 配置相同的两个环境变量即可，不需要挂载 database.local.json：

| 环境变量 | 内容 |
| --- | --- |
| `BENCH_DB_USER` | 应用数据库账号 |
| `BENCH_DB_PASSWORD` | 数据库密码，通过平台 Secret 注入，按原值填写 |

修改后重新部署/重启 Web 和 Worker。连接使用普通 MySQL 协议，不使用 JDBC URL；密码无需 URL 编码。需要 TLS 时在 deployment/database.json 中添加 `ssl` 对象（如 `"ssl": {"ca":"/path/to/ca.pem"}`），证书文件需在两个服务都可读取。该文件不允许存放账号密码。

只要设置账号或密码中的任意一个，就要求两者完整且非空，不会从旧文件补齐凭据。两者均未设置时，仍兼容已有本地 database.local.json（或 cluster.json 的 database_config 指定文件）；没有本地文件则提示补充这两个环境变量。部署方式不需要 database_config 字段，也不再读取 BENCH_DB_HOST、BENCH_DB_PORT、BENCH_DB_NAME、BENCH_DB_SSL，旧部署可移除这四个变量。数据库地址切换时修改 deployment/database.json 并重新构建镜像。

使用具有建表权限的账户显式执行一次（可由 DBA 使用 `backend/src/scheduling/schema.sql` 和 `backend/src/scheduling/web_schema.sql`）：

```sh
python -m scheduling --scope dev initialize
```

原先已建好 6 张调度表的环境，只需 DBA 补执行 `backend/src/scheduling/web_schema.sql`，新增 `bench_web_state` 一张表（合计 7 张）；运行账户对此表也需 SELECT/INSERT/UPDATE 权限。应用启动不执行 DDL。

建表完成后，不再执行 configure/pool 初始化命令；Web 启动时自动写入调度配置。运行账户需要调度表的 SELECT/INSERT/UPDATE 权限，无需建表权限。st/dev 建议不同数据库、账户、COS 前缀；scope 是逻辑隔离，不替代访问权限。

### 2. 启用集群

各实例的 `deployment/cluster.json` 使用相同环境配置：

```json
{
  "mode": "mysql",
  "scope": "dev"
}
```

cluster.json 指定模式、环境，数据库地址来自 deployment/database.json，账号密码通过环境变量注入。Web 启动自动初始化默认并发；Worker 只读取数据库，不会互相覆盖限制。Worker 先启动时等待 Web 完成初始化，不需人工补命令。

日常唯一可选的执行设置是 `"concurrency": 2`，表示整个环境最多同时领取 2 个任务。在所有 Web 的 cluster.json 使用相同字段值并重启 Web 即生效，无需重启 Worker。降低上限不打断正在执行的任务，只限制后续领取。该上限覆盖资源初始化、导入、ZIP 工具、准备、案例和汇总任务，不是模型请求的 RPM/TPM 限流器。

新环境未填写 concurrency 时默认 5。已有环境未填写时继承数据库限额；旧全局和池上限不一致时取其中最小值，避免升级扩大模型压力。当前 localtest 已配置为 2，升级后仍为 2。启动日志会打印实际生效值。旧 pool/model_pools/worker_slots/lease_seconds 字段不再作为用户设置；旧池标识仍保留供已冻结批次使用。每个 Worker 内部容量固定为 5，集群需要更高吞吐时增加 Worker，但全局上限仍需结合模型额度决定。

更新时保留本机已启用的 mode、scope 和数据库环境变量；仍使用文件连接的本地环境保留 database_config；不要用默认 single/dev 模板覆盖正在验证的 mysql/localtest 配置。测试环境和正式环境分别初始化，各自的限额不会自动复制。

同时配置原有 COS 资源存储为 cos。模型私有前缀、资源前缀和运行证据前缀均需可访问。Web 和所有 Worker 使用相同工具发行版本和服务端 Agent 配置；不同版本 Worker 可并存，但只能接匹配任务。

同一镜像部署 Web、Worker 两个服务单元，分别填写启动命令，无需增加角色环境变量：

```sh
/opt/deployments/.venv/bin/python -m deployment.container --role web
/opt/deployments/.venv/bin/python -m deployment.container --role worker
```

命令行角色优先于已有 `BENCH_CONTAINER_ROLE`，不填写时兼容原有环境变量和单实例 all 入口。多实例部署使用明确的 web / worker 角色；数据库地址使用 deployment/database.json，账号密码使用 BENCH_DB_USER/PASSWORD 环境变量，集群模式、scope、并发仍在 cluster.json 中配置。若平台按参数列表录入命令，应把可执行文件及每个参数分别填写，不额外套一层后台 shell。

本地调试也支持：启用集群配置后，页面启动入口自动切换；另运行 `python -m webui.worker` 启动 Worker。每个 Worker 启动生成独立身份。

### 3. 历史数据与回退

集群列表只展示 MySQL 新登记的批次。旧 SQLite 批次与 COS 整批备份没有自动导入，本次不会迁移或删除历史数据；保留原单实例环境供历史查询。不能直接让新旧部署共写同一资源前缀。回退前先停集群领取与 Worker，再把 mode 改回 single；不会把 MySQL 排队任务自动转成 SQLite 任务。

## 双 Web 与双集群部署（2026-11-16）

平台在两个集群各部署一个实例时，Web 服务单元和 Worker 服务单元都填 1，实际是 2 个 Web + 2 个 Worker。两个 Web 使用相同数据库、scope、COS 前缀、站点域名和代码版本。全局 concurrency 仍是整个 scope 的上限，不乘以集群数量。数据库和 COS 必须从两个集群均可访问，Web 之间不用直连。

- 上传分块先写 COS 并回读校验，再用 SQL 版本条件推进偏移。刷新或请求切换实例后，重新选择同一文件可从已确认偏移继续。浏览器刷新仍会中断当前 HTTP 传输，不能在文件尚未发出时凭空续传。
- 资源处理由独立 Worker 执行，集群 Web 不再启动资源处理线程。资源与测评共用 bench_scheduler_tasks / attempts、并发限制和 LeaseGuard：90 秒租约、每 30 秒续期，资源中断最多领取 3 次，每次记录保留。普通格式错误直接失败，不自动重跑。资源运行约每 5 秒上传进度和日志，完成后目录指针与任务终态在同一事务发布。Worker 停止或续期失败时会终止对应子进程及后代；旧租约不能发布结果。
- 校验在独立临时目录完成。共享资源清单与成功状态在同一 SQL 事务中发布，半成品不进入另一个 Web 的可选列表。两个 Web 可同时服务页面；资源导入沿用串行处理，ZIP 工具最多同时保留 5 个活动文件。
- 模型新增、修改、删除发布私有 COS 快照，再条件更新数据库版本。并发冲突会提示刷新重试，不覆盖另一实例的修改。已创建批次继续使用其独立冻结模型配置。
- 页面会话和下载签名使用 scope 内共享令牌；容器重启或请求切换实例不再因为各自生成随机令牌而报会话失效。不同 scope 的令牌独立。
- ZIP 工具的上传、处理状态及下载文件也共享；从一个实例申请下载链接，可由另一个实例提供文件。处理成功后保留 24 小时的下载入口；接收中的文件保留 7 天。
- Skill 在集群模式使用 SQL 资源清单作为发布入口；原包、文件清单和内容身份不变，COS 对象均回读校验。相同版本按已有身份保留，重打包保留原 ZIP。此处替代单实例 ADR 0004 的 COS 追加标记发现机制，单实例仍使用原追加协议。

首次启用时 Web 只提交一个共享初始化任务，由 Worker 将现有 COS 案例和 Skill 清单、模型配置转入共享目录。初始化期间 Web 存活检查正常、就绪检查返回 503，资源接口提示等待 Worker；无需由用户执行额外初始化命令。初始化明确失败后，修复配置并重启 Web 可重新排队，保留旧尝试记录。之后只读数据库指向的资源版本，禁止旧单实例部署继续共写这些前缀。升级应先停旧 Web 的资源执行，再发布新 Web 和 Worker；只有尚未应用 web_schema.sql 的环境需要补表。未结束的共享资源任务由新 Worker 登记到统一队列，不能让旧资源执行线程与新 Worker 混跑；不要让不支持共享目录的旧 Web 混在流量中。新的资源目录和模型修改不会反向更新旧单实例索引，因此不能仅切回 single 就认为新资源已完整恢复。

数据库中的版本指针与 COS 对象共同构成持久化数据，必须一起备份。逻辑删除/过期会撤销共享记录或下载入口；当前未实现 COS 无引用对象的物理回收，不要直接给整个运行前缀配置短期自动删除，以免删掉仍被批次引用的文件。

本轮专项验证采用两个独立本地数据目录、真实 Flask 路由、SQLite 事务替身和文件型 COS 替身，未调用真实模型或真实 COS：跨 Web 多分块续传与重复分块拒绝、共享导入进度和案例列表、模型增改删、Skill 原包下载、租约过期接手与旧所有者拒写、真实小型 Git 仓库 ZIP 转换与跨 Web 下载签名、目录版本冲突拒绝、仓库 ZIP 导入与不可变 bundle 取回。第三个空目录 Web 能恢复资源与模型目录，并使用已有会话读取页面状态；批次冻结模型仍走原持久化接口。没有新增测试文件，按用户要求未跑浏览器 E2E。

本轮 `npm run verify` 已通过（使用临时 npm 缓存），包括现有静态检查、Node 检查、前端构建和差异检查；不包含已移除的 Python 单测，也不代表真实 TDSQL/COS 验收。

行内 dev 验收仍需确认真实 TDSQL/COS 权限和事务行为：两个集群交替访问同一上传；处理中停止一个 Worker，等待另一 Worker 接手；再运行原两例批次，确认只生成一份有效汇总。上述本地替身验证不等于完成双集群验收。


## Worker 职责拆分与 EXEC 健康检查（2026-11-16）

本轮不新增数据库表，也不改变已有批次的冻结输入、模型、工具身份和评分口径。已有七张表继续使用；bench_web_state 中旧资源租约列保留但不再参与领取，任务身份、租约、进度检查点和尝试记录统一由调度表保存。资源任务不出现在测评批次列表中，不会触发评分。案例任务仍保留原质量/稳定性模式的接手上限，资源重试不能改变案例首次成功率。

- Web：验证请求、上传文件分块、管理配置、登记任务、读取共享状态及文件。资源和模型目录只是从 COS 下载的本地缓存，进程重建可丢弃。页面读取仍可能发生缓存下载，并不承诺所有请求固定毫秒响应。
- Worker：资源初始化、ZIP 解压校验和转换、仓库导入/准备、检视、评分与报告。每次任务独立子进程和临时目录；资源子进程仅写临时进度和不可变 COS 文件，由持有租约的父进程发布结果。
- 数据库：共享状态、任务和执行尝试、资源版本指针。COS：文件与证据。没有共享本地目录要求。

Worker 的探针选择 EXEC，使用以下命令（平台若要求参数数组，逐项填写）：

```sh
# 就绪检查
/opt/deployments/.venv/bin/python -m scheduling.health ready
# 存活检查
/opt/deployments/.venv/bin/python -m scheduling.health live
```

命令成功退出 0，失败退出 1；不访问数据库、COS 或模型，只读本实例 Worker 写入的心跳。Worker 主调度循环写心跳，不能用与任务调度无关的独立线程假报存活。就绪要求进程存在、最近 30 秒内调度循环正常、最近一轮数据库操作成功且共享目录已初始化。存活要求进程存在且循环心跳未超过 180 秒；数据库短暂故障会降为未就绪，但循环仍可存活。长案例正在子进程执行不会阻塞主循环，也不会因为尚未产出结果而误判卡死。停止领取后立即标记 draining，再等待子进程清理。

探针可先沿用页面的启动后 30 秒、间隔 30 秒、超时 5 秒、连续失败 3 次参数，在 dev 验证后调整。Web 仍使用 HTTP /healthz、/readyz；不要把 Web HTTP 探针复制给 Worker。Worker 无业务 HTTP 端口或域名，平台基础设置的监听端口是否可留空需要部署时核实，不能因为填了一个数字就认为进程已监听。

本地启用 mysql 模式后仍是 npm run dev 启动页面，另开终端运行 .venv 对应 Python 的 `-m webui.worker`。不启动 Worker 时资源任务会排队，不在 Web 中临时执行。默认 single 模式保留原运行方式；本次职责拆分针对 mysql 集群模式。
