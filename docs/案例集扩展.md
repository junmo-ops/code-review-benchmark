# 案例集扩展与模块边界

当前支持 `aacr`、`swe_prbench_llm` 和历史兼容的 `swe_prbench`，被测工具支持 `lcr`。新 SWE 协议只计大模型确认的匹配，不再要求嵌入评分。下文 `swe_prbench` 指历史协议。SWE-PRBench 以明确命名的 `lcr_repository_variant` 接入，复用原始标注、裁判提示词与维度评分，但不满足官方固定上下文和嵌入评分协议。详见[双案例集试跑](双案例集试跑.md)。未知案例集仍立即报错，不套用 AACR 评分。

## 模块职责

| 模块 | 职责 |
|---|---|
| `runner/` | 批次、数据冻结、状态、能力检查、子进程超时与落盘、导出 |
| `reviewers/lcr/` | LCR 命令、原始输出解析、完整答卷转换、恢复及 LCR 日志 |
| `suites/aacr/` | AACR 数据加载/转换、评分调用、请求审计、中文报告 |
| `vendor/aacr/` | 从原 framework 迁入的上游代码本地快照、许可证、文件哈希 |
| `data/sources/` | 各案例集的原始记录、来源、抽样说明 |

调用关系：`local.py` → `cloud.py` → `runner/cloud.py` → 选定的案例集适配器 / LCR 适配器。

执行器传给 LCR 的 `ReviewCase` 只有案例 ID、仓库和两个完整提交 SHA。参考答案保留在案例集文件中，由对应评分器加载。工具自身能够访问的文件系统并非安全沙箱；这里保证的是不通过案例对象、命令参数主动传入参考答案。

## 接入一套案例集

1. 核对任务定义、许可、上游版本和评分协议。保存来源 URL、commit/release、原始数据哈希、抽样规则和随机种子；未保存的信息明确标为未知。
2. 在 `suites/<id>/` 实现 `runner/contracts.py` 中的接口。`load_cases()` 验证本套数据并返回 `ReviewCase`；特殊标签和参考答案仍保存在原始/转换后文件里，不塞进 LCR 输入。
3. 定义 `required_capabilities`。当前 LCR 适配器只声明 `git_range`、`findings`。需要测试执行、多轮交互或额外背景的基准，必须先增加相应能力；不得删掉这些任务条件后继续评分。
4. 实现 `identity()` 固定适配器版本、评分源码/依赖快照哈希，`provenance()` 保存数据来源，`parameters` 声明本套评分默认参数。`convert()` 转换格式；`evaluate()`、`report()` 使用该套自己的评分和报告格式。
5. 在 `suites/registry.py` 注册。当前采用显式注册，不从数据文件导入任意 Python 模块。
6. 准备案例仓库 Git bundle。用 `tools/setup.py --suite <id> --dataset <清单> --repos-only` 按清单恢复对应仓库。完整安装仍受当前 Linux x86_64/Python 3.11 资源包约束。
7. 先验证五例：转换与参考信息保真、无答案泄漏、预览范围、完整/部分答卷处理、超时/恢复、评分正确性、报告及导出。对齐评分协议后才扩大范围。

AACR 示例：

```bash
.venv/bin/python tools/convert_dataset.py --suite aacr \
  --input data/sources/aacr/pilot5.raw.json \
  --output data/aacr-pilot5-converted.jsonl --seed 42

.venv/bin/python local.py --timeout-seconds 60 init \
  --suite aacr --run-id aacr-local-01 \
  --dataset data/pilot1.jsonl --timeout-minutes 10
```

转换会使用上游转换器的排序/抽样行为，输出顺序可能与已有 pilot 清单不同。输出已存在时拒绝覆盖。转换后的自定义清单若不匹配已知数据哈希，批次会标为 `unverified_custom_dataset`，需要补充来源记录后再用于正式比较。

## 批次与评分隔离

新批次 `run-config.json` 的 `schema_version=2` 固定：

- 案例集 ID、适配器版本、评分代码哈希、评分参数、数据来源快照；
- 数据清单哈希、案例 ID；
- 检视工具及规则哈希、检视模型/接口摘要、并发与超时；
- init 时已提供的裁判模型/接口摘要；评分时写入最终 `evaluation-config.json`。

后续命令从批次配置选择评分器，不允许中途改 `--suite`。评分器变化时阻止继续评分，status/next/export 仍可读取记录。每个案例集使用独立 run-id；不跨案例集合并 Precision/Recall/F1。

AACR 上游使用 `config`、`judge`、`pipeline` 等顶层模块名，且本地有请求审计包装，因此评分/报告在独立 Python 子进程中执行，防止影响其他评分适配器。现有 AACR 的 `metrics_ocr_*.json` 文件名暂保留为该适配器的兼容细节，不是所有案例集的约定。

历史 schema_version=1 批次按本项目原有 AACR 流程兼容读取，并显示“历史批次未冻结评分器版本”；不回写伪造来源或版本，不迁移已有答卷和分数。

## 上游源码管理

`vendor/aacr/UPSTREAM.json` 固定的是当前本地继承快照。此前上游 commit 和修改记录没有保留，不能标成官方某个发行版本，也不能宣称完成许可审计。此次迁移没有改动 vendor 中原有文件内容。后续更新需固定上游 commit、核对许可证/NOTICE、记录差异并创建新批次。

AACR 数据当前仍是五例 Cline 接入样本；不能代表完整基准或正式的跨语言抽样。

## 何时拆开部署

不同案例集可以在同一仓库维护，但独立安装依赖或打包运行环境。只有任务生命周期、平台依赖或维护发布边界明显不同，才拆成独立运行包乃至独立项目；共用的批次和日志接口仍可复用。当前代码没有新增容器、调度服务或插件安装系统。


## Martian 裁判接入（2026-10-01）

裁判层已拆到 evaluators/：案例集由 suites/ 负责输入映射，Martian 的匹配与评分在独立适配器中复用上游。新增案例集需要显式添加参考意见映射及支持声明；未知案例集不自动套用。原套件评分留作 original。详见[裁判对比](裁判对比.md)。


## CodeFuse 扩展实现

新增 suites/codefuse_cr，保留官方原始行；提供 reference_comments 和 check_repository。scoring/ 是新套件入口，复用 evaluators/ 中已冻结的 Martian transport、上游评分和报告；旧批次仍按原引擎及哈希运行。这样添加套件不会改写已有 Martian 批次身份。CodeFuse 不支持 original，创建批次时直接拒绝，不回退 AACR。

当前扩展使用 code-only 输入，不自动把官方 issue 背景或最终 merged_patch 传给 reviewer。接口若扩展背景能力必须新协议、新批次，不能静默改变现有对照条件。
