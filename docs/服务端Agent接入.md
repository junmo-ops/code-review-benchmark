# 服务端 Agent 接入

## 唯一配置入口

本地和容器统一读取项目根目录的 `agent.json`。配置随代码发布，不需要进入容器修改文件。

- 默认服务地址：`https://llm-agent.paas.cmbchina.cn`。
- 本地联调：将同一个文件的 `base_url` 改为 `http://127.0.0.1:8000`。
- 切回远程服务：将 `base_url` 改回默认域名。
- 地址只填服务根地址，不追加接口路径；新域名的 HTTPS 连通性仍需行内验证。
- 修改配置后重启平台，新建批次验证；不要在任务运行中修改，也不要将旧服务任务 ID 用于新服务查询。

已移除旧示例文件及 `agent.local.json` 的读取逻辑，`BENCH_AGENT_CONFIG` 不再生效，`BENCH_CONFIG_ROOT` 不控制此配置。旧部署即使留有这些设置也不会覆盖 `agent.json`。升级前仅迁移需要保留的非敏感连接选项，不迁移旧仓库映射、密码或令牌。

统一使用新案例集，`repo` 直接填写完整行内仓库标识，例如 `S990768/LV01.30_Checkmate`。公司协议检查 `S数字/项目名` 格式，直接发送且按相同名称校验响应，不再转换开源仓库名。`agent.json` 不再接受 `repositories` 字段；旧案例集需更新后再创建测评。历史批次不自动改写。

## 公司接口

协议为 `company-repo-review-v1`，无需鉴权，不发送模型 API Key。公司协议不使用 `BENCH_AGENT_TOKEN`。

- 创建：POST `/repo-review/async-report`，发送 `repo_name`、`commit_ids: [start, end]`、`review_mode: from_to`。
- 查询：GET `/review-report-scan/report/{report_id}`，要求业务成功码 `SUC0000`，从 `body.report` 读取结果。
- 新批次直接比较案例 base/head，不由平台克隆仓库；历史 merge-base 批次保留原有口径。
- `PROCESSING` 继续等待，`SUCCESS` 校验并转换答卷，`FAIL` 不作为零问题成功评分。
- 核对报告 ID、仓库名、起止 SHA 和 `FROM_TO` 检视范围。行号按 end 版本解释，缺失位置或描述时保留原始响应并报错。
- 当前服务固定使用 DeepSeek，具体版本未确认；平台选择的模型不代表服务端实际模型，裁判配置独立。
- `extra_info.token_usage` 提供用量，缺失或无效时标为未知；错误信息来自 `extra_info.error`。
- 未确认服务支持创建幂等。创建响应不明时先核对服务端，不自动重新提交。

配置及适配代码身份随批次冻结，升级后历史批次可能需要原运行时，不改写冻结身份绕过检查。

## Windows 本地联调

先启动 Agent，将 `agent.json` 的 `base_url` 改为 `http://127.0.0.1:8000`，然后在项目根目录执行：

```powershell
npm run dev
```

前端通常为 5173，平台后端为 8765，Agent 为 8000，以实际启动输出为准。选择服务端 Agent，先新建 Checkmate 单案例测评，不要在接口文档页重复创建任务。

`127.0.0.1` 指测评后端所在机器；容器或跨机器调用不能照用本机地址。请求由 Python 后端发起，不需要浏览器跨域配置。

服务端自行访问 Git、模型和数据库。仓库请求为 `S990768/LV01.30_Checkmate`，Git 域名由服务端的 `GIT_REPO_URL` 模板确定，平台不发送完整克隆 URL。

## 旧模拟协议

代码保留 `review-service-v1-draft` 协议兼容能力，但不再提供独立模拟配置文件或默认启用模拟服务。真实公司接入保持 `agent.json` 中的公司协议即可。历史模拟批次仍不得输出正式答卷或评分。

## 超时、恢复与证据

新建服务端 Agent 测评默认等待 60 分钟，可在高级参数中调整为 1–120 分钟；已有批次保留创建时的时限。服务端模式的“超时分钟数”是每案例本地等待时限，不是服务端模型时限。关闭工作台或停止本地进程不代表取消远端任务。回到原批次，选中案例后点「从已有输出恢复结果」，只使用已保存 task_id，不再创建任务。

raw 目录保存创建意图、幂等键、task_id、原始结果、执行状态及追加事件日志；正式成功输出才进入 results。创建请求未收到 task_id 时暂停，交由维护方核对，不自行猜测。

真实联调首轮只跑 1 例：确认服务取得相同仓库和提交范围、实际模型、完整意见、引擎版本，然后才评分及扩大范围。工作台暂不支持自动发现服务端可用模型；请求模型不受支持时应由服务明确拒绝。

服务端等待超时后，本次自动流程停止，不继续自动评分。任务 ID 和请求保留；确认服务端完成后，在原批次选中案例恢复查询，成功后再点击评分。

### 检视耗时口径

公司 Agent 的检视耗时取报告 `trigger_at` 到 `completed_at` 的间隔，包含服务端排队、检视和报告处理，不是纯模型调用时间。平台等待和恢复查询耗时仍单独保存在执行记录中，不叠加到服务端检视耗时。缺少时间、格式无效、结束早于开始、或仅一端带时区时，不推测耗时。

新答卷保存 `duration_seconds` 和来源标记。旧答卷已保存 `service.timing` 的，重新生成中文报告时可直接补展示；不会重写已评分答卷、旧 metrics 或评分缓存。结果对比同样按该时间读取，重复生成报告不会累计。若旧批次入口因冻结版本校验阻止操作，可用只读展示命令生成报告：`python -m suites.aacr.report <批次目录> --offline`，无需重新检视或评分。
