# 宕机定位日志

服务端默认开启（`BENCH_SERVER_MODE=1`），不调用模型或 COS 验证接口。

- 平台标准错误日志：搜索 `[bench-diag]`。必须确认部署平台会采集并保留 **stderr 和上一容器日志**；应用本地副本不能替代容器外采集。
- 本地副本：`BENCH_DATA_ROOT/ui-state/diagnostics/events-<PID>.jsonl`。每进程当前文件与 previous 文件各最多约 4 MiB，超限滚动；容器临时目录重建可能丢失。本副本不自动备份到 COS，避免新增备份负载。
- 配置：`BENCH_DIAGNOSTICS=0` 关闭；`BENCH_DIAGNOSTICS_INTERVAL_SECONDS=5` 将资源采样从默认每秒调整为每 5 秒。有效范围 1–60 秒。

## 记录内容

所有记录为带 `[bench-diag]` 前缀的单行 JSON。`timestamp` 使用 UTC；`boot_id` 标识本次容器启动，`pid` 标识进程，`trace_id` 关联同一次 API 请求。`process_id` 区分 PID 被复用的进程生命周期。

| 事件 | 用途 |
| --- | --- |
| `http.begin/end/failed` | `/api/jobs`、`/api/state`、多模型创建请求开始、HTTP 状态、耗时；响应提供 `X-Benchmark-Request-Id` |
| `benchmark.submit.*`、`profile.*`、`queue.*` | 提交校验、固定模型配置本地保存/持久化、队列写入、状态刷新、排队/运行任务数 |
| `worker.claimed/finished/heartbeat/signal` | 是否真的启动第二批任务、Worker 存活、退出信号 |
| `benchmark.stage.*` | init/check/review/eval 等阶段开始、结束、异常类型及耗时 |
| `backup.*` | 备份整体、会话/批次/日志分组、队列快照与队列提交，识别长时间卡住的阶段 |
| `container.*` | 启动、子进程 PID 和角色、退出码、停止信号、关闭流程 |
| `resources.sample` | 容器 cgroup 内存当前值/上限/峰值/事件、CPU 计数；当前容器父进程及后代的 RSS、CPU ticks、PID/PPID（最多列出内存最大的 12 个进程） |

不记录请求正文、模型配置内容、API Key、认证头、命令行、环境变量或异常消息。错误只记录类型，原有业务日志仍用于查看经过脱敏的详细报错。

## 复现与判断

先确认备份状态，再用一个案例启动测评观察日志；复现 50 例时只观察开始后的几分钟，保留宕机前日志，不需要等待整轮跑完。

- 单个 50 例也崩溃：查看 init/check/review 阶段切换、`resources.sample` 的进程内存以及同时间的 `backup.*`。
- 加入排队任务后崩溃：对齐 HTTP 请求的 trace_id，查看 profile/queue 分段是否完成，是否出现第二个 `worker.claimed`。
- `memory_events` 的 oom/oom_kill 增加是内存杀进程线索；仅凭 137 退出码或 RSS 接近上限不能直接认定 OOM。
- `container.child_exit` 会指出哪个服务进程先退出及其退出码。`container.signal` 表示应用收到了 SIGTERM/SIGINT，但不能单独确定平台发送信号的原因。
- 强制 SIGKILL/OOM 时不会产生正常关闭日志。需要结合平台终止原因/探针事件；即使它们缺失，最后的容器外采样仍能帮助缩小范围。
- 进程 RSS 总和包含共享页重复计数，不能当作容器实际用量；判断内存容量优先用 cgroup 的 memory_current / memory_limit。CPU ticks 为累计值，并非 CPU 百分比。

本地 lint、构建和合成验证不代表行内宕机已复现或根因已经确定。


## 仓库准备与工作目录的资源控制

- 测评开始先逐仓库验证实际 base/head 提交和共同历史；全部可用时直接复用，不读取或下载 bundle。仓库缺失或提交不足才恢复历史。
- bundle 缓存首次使用执行 SHA256 校验，并保存本地 `.verified.json` 记录。记录关联路径、设备、inode、大小、mtime、ctime 和预期摘要；文件变化、替换、记录缺失或异常都会重新校验。此记录只加速本地缓存，不替代新上传文件的完整性校验。
- `repository.check`、`repository.bundle`、`repository.restore` 记录逐仓库耗时；`repository.bundle_cache.hit/miss` 表示本地文件校验是否可复用。工作台任务消息和执行日志显示仓库序号及操作阶段。
- 案例获得并发名额后才创建 Git worktree，已完成答卷跳过时不创建；工作区创建与清理串行，检视仍按案例并发执行。案例所有重试结束后清理，清理失败会保留目录并记录错误。
- 答卷和原始日志保存在批次目录，LCR 会话保存在用户主目录下 `.leancodereview/sessions`，不随 worktree 清理。续跑重建相同路径与提交；已有异常遗留 worktree 不会自动覆盖。
- 这些措施减少重复 I/O 和同时存在的工作目录，不承诺容器文件缓存立即下降，也不构成此前宕机原因已确认的证据。
